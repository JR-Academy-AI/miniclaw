# 子目录 AGENTS.md（强制）

大的功能模块、component、多 provider 目录必须在目录下放一份目录级说明，记录**读代码看不出来**的东西：职责边界、契约、不变量、坑、扩展方法。它是让任何 AI agent（Claude Code、Codex……）和人在改这块代码时不踩坑的最直接手段。

## 文件约定（跨工具，必须遵守）

- **内容只写在 `AGENTS.md`**：这是 Codex 等工具通用的约定
- 同目录再放一个 `CLAUDE.md`，**全文只有一行** `@AGENTS.md`：Claude Code 读取目录内文件时会自动加载该目录的 `CLAUDE.md`，并通过 `@` 引用拿到同一份内容
- 禁止在 `CLAUDE.md` 里写独立内容，两份内容迟早走样（`02-dry.md`）
- 并非所有工具都会自动加载子目录的说明文件（例如 Codex 只加载从项目根到当前工作目录路径上的 `AGENTS.md`），所以根目录 `AGENTS.md` 要求：**修改某目录下的代码前，先读该目录及其各级上级目录中的 `AGENTS.md`**

## 哪些目录必须有

| 目录类型 | 判定标准（满足任一） | 放在哪 |
|----------|---------------------|--------|
| **大功能模块** | core 下的一级模块（router / scheduler / skill registry / session store 等）；或目录内 ≥ 5 个源文件；或代码 ≥ 500 行；或包含按 `00-overview.md` 标注过"原则例外"的复杂函数 | 模块根目录 |
| **Component** | TUI 的 component 分组目录；或单个 component 带自身状态 / 异步逻辑 / ≥ 150 行（此时它应独立成目录） | component 目录 |
| **多 provider** | 同一接口有 ≥ 2 个实现：runtime adapter（Claude Code / Codex）、模型 provider、computer-use 执行器、存储后端等 | **父目录**必须有；单个 provider 有非显而易见的怪癖时，其子目录也要有 |
| **规范 / 文档目录** | 存放规则、需求、设计规范的顶层目录：`docs/`、`rules/`、`design/`（design system）；以后新增同类目录同样适用 | 目录根；写清每个文件的权威范围、改动时必须同步的地方 |

新建符合条件的目录时，`AGENTS.md` + `CLAUDE.md` 与代码**同一次改动**提交；已有目录长到满足条件时，在那次改动里补上。

## 写作要求

- **≤ 80 行**。它每次都会被加载，长了就是噪音
- **只写代码里看不出来的**：为什么这样设计、有哪些不变量、哪里容易改错。不复述函数签名、不列文件清单（遵守 `02-dry.md`，代码才是权威来源）
- **与代码同步**：改了契约、不变量、扩展方式，必须在同一次改动里更新对应 `AGENTS.md`。过期的说明比没有更糟
- 通用原则不要重复写，引用 `rules/` 即可；这里只写本目录特有的规则
- 用祈使句写规则（"必须 / 禁止"），不写散文

## 模板

### 大功能模块

```markdown
# <模块名>

## 职责
一句话：这个模块负责什么。**不负责**什么（边界最容易被越过的地方写出来）。

## 对外契约
- 对外暴露的接口 / 入口，以及调用方可以依赖的保证
- 依赖哪些抽象（不写具体实现）

## 不变量
- 任何改动都必须保持成立的条件（例：同一 schedule 同一时刻只运行一个实例）

## 容易改错的地方
- 坑 + 原因 + 正确做法

## 测试
- 测试位置、如何运行、改动后必须跑哪些
```

### Component

```markdown
# <component 名>

## 职责
展示什么、接收哪些数据、发出哪些意图（intent）。不得包含业务逻辑（见 `04-other-principles.md`）。

## 状态
- 自身持有哪些状态、哪些来自外部；状态变化的触发来源

## 交互约定
- 快捷键、焦点、滚动、空状态 / 加载中 / 错误态的表现

## 容易改错的地方
- 例：长输出渲染性能、终端尺寸变化、异步结果回来时组件已卸载
```

### 多 provider（父目录）

```markdown
# <provider 类别，如 runtime adapters>

## 统一契约
- 所有 provider 必须实现的接口，以及语义约定（错误类型、取消 / 超时、流式事件格式）
- 能力差异通过 `capabilities` 声明，禁止抛 NotImplemented（见 `01-solid.md` LSP）

## Provider 对比
| provider | 能力 | 认证方式 | 限制 / 配额 | 备注 |
|----------|------|---------|------------|------|

## 新增 provider 步骤
1. 新建 `<provider>/` 子目录并实现接口
2. 在注册表中注册（不改核心流程，见 `01-solid.md` OCP）
3. 通过契约测试：<测试位置>
4. 更新上方对比表 + `CHANGELOG.md`

## 容易改错的地方
- 跨 provider 的公共逻辑放在哪（重试 / 超时 / 日志），禁止在单个 provider 里各写一份
```

### 单个 provider（仅在有怪癖时）

```markdown
# <provider 名>

## 与统一契约的差异 / 怪癖
- 例：该 SDK 流式事件无结束标记，需以进程退出判定结束

## 外部依赖
- SDK / CLI 版本要求、认证、环境变量
```
